# Техническое задание: UI/UX-улучшение TeamBook

## 1. Цель

Повысить удобство и визуальную целостность TeamBook без изменения бизнес-логики, структуры данных и существующих пользовательских сценариев.

Основные результаты:

- уменьшить визуальную плотность интерфейса;
- скрыть второстепенные действия до момента запроса;
- улучшить информационную и типографическую иерархию;
- унифицировать компоненты;
- разделить конкурирующие режимы канбана и календаря;
- улучшить карточку сотрудника;
- сохранить светлую и тёмную темы, адаптивность и доступность.

---

## 2. Ограничения

### 2.1. Запрещено

- изменять бизнес-логику приложения;
- изменять структуру SQLite без отдельного обоснования;
- добавлять роли, пользователей или разграничение доступа;
- превращать приложение в SPA;
- добавлять тяжёлый JS-фреймворк;
- заменять серверный рендеринг Jinja;
- добавлять горизонтальную прокрутку канбан-колонок;
- менять календарь месяца на горизонтальную диаграмму Ганта;
- возвращать системную колонку «Бэклог» в канбан;
- возвращать удалённые шаблоны быстрого добавления;
- удалять существующие функции;
- ухудшать управление с клавиатуры;
- использовать внешние CDN-зависимости без необходимости.

### 2.2. Необходимо сохранить

- Flask + Jinja;
- текущие маршруты и формы;
- CSRF-защиту;
- светлую и тёмную темы;
- drag-and-drop задач и колонок;
- серверные POST-операции;
- модальные окна редактирования;
- мобильную адаптивность;
- текущие тесты;
- работу без JavaScript для обычных HTML-форм там, где она уже доступна.

## 3. Объём работ

## Пакет 1. Базовая дизайн-система

### 3.1. Расширить CSS-токены

Файл:

- `static/style.css`

Добавить или унифицировать токены:

```css
--space-1
--space-2
--space-3
--space-4
--space-5
--radius-sm
--radius-md
--radius-lg
--shadow-sm
--shadow-md
--focus-ring
--warning
```

Существующие переменные цветов сохранить. Новые компоненты должны использовать токены, а не случайные числовые значения.

### 3.2. Типографическая шкала

Создать классы:

- `.page-title`;
- `.section-title`;
- `.card-title`;
- `.body-text`;
- `.meta-text`;
- `.helper-text`.

Требования:

- заголовок страницы: 24–28 px;
- заголовок секции: 18–20 px;
- заголовок карточки: 15–16 px;
- основной текст: 14–15 px;
- метаданные: 12–13 px;
- у каждого уровня должна быть стабильная высота строки.

### 3.3. Общий фокус

Добавить выраженный `:focus-visible` для:

- ссылок;
- кнопок;
- полей;
- `select`;
- `textarea`;
- `summary`;
- интерактивных карточек;
- элементов с `tabindex`.

Нельзя полностью убирать outline без равноценной замены.

### 3.4. Уменьшение анимации

Добавить:

```css
@media (prefers-reduced-motion: reduce)
```

В этом режиме отключить необязательные transition и animation.

### 3.5. Убрать inline-стили из основных шаблонов

Вынести повторяющиеся правила в классы, прежде всего из:

- `templates/index.html`;
- `templates/board.html`;
- `templates/todo.html`;
- `templates/employee_view.html`;
- `templates/settings.html`.

Допускаются inline CSS-переменные для динамического цвета тегов, например `--c`.

Не выполнять механическое удаление всех inline-стилей за один раз, если это создаёт большой нерелевантный diff.

## Пакет 2. Унифицированные компоненты

### 4.1. Заголовок страницы

Создать общий паттерн:

```html
<div class="page-header">
  <div class="page-header-main">
    <h1 class="page-title">...</h1>
    <p class="page-subtitle">...</p>
  </div>
  <div class="page-actions">...</div>
</div>
```

Использовать на страницах:

- сотрудники;
- доска;
- мои задачи;
- проблемы;
- справочники;
- настройки;
- формы сотрудника;
- формы встречи.

На мобильном действия должны переноситься под заголовок.

### 4.2. Панель фильтров

Заменить разрозненные:

- `.compact-filter`;
- `.kb-filter-bar`;
- `.todo-filterbar`;
- фильтры на базе `.filter-row`;

на единый компонент `.filter-bar`.

Компонент должен поддерживать:

- поисковое поле;
- селекты;
- toggle-chip;
- кнопку сброса;
- перенос на мобильных устройствах;
- подпись количества найденных элементов.

Панель должна оставаться компактной и не превращаться в крупную секцию-карточку.

### 4.3. Меню действий

Создать доступный компонент `•••` для второстепенных действий.

Требования:

- непрозрачный фон на базе `--panel2`;
- `aria-expanded`;
- `aria-controls`;
- закрытие по Escape;
- закрытие по клику вне;
- возврат фокуса на триггер;
- управление с клавиатуры;
- опасные действия визуально выделены;
- элементы меню не переносятся на несколько строк.

Использовать существующий паттерн меню «Ещё» в `base.html`, но вынести общую JS-логику, чтобы не копировать отдельный обработчик для каждой карточки.

### 4.4. Пустые состояния

Создать компонент `.empty-state`:

- необязательная иконка;
- короткий заголовок;
- пояснение;
- необязательное действие.

Не использовать один символ `—` в качестве основного пустого состояния.

Разделить показатели на смысловые группы.

### 5.2. Цветовая семантика

Красный стиль применяется только к:

- просрочке;
- проблемам;
- ошибочным или критическим состояниям.

Наличие обычных задач не должно автоматически отображаться красным.

### 5.3. Метрики

Обновить `.stat-card`:

- сделать различимыми обычное и критическое состояние;
- добавить подписи без двусмысленности;
- сохранить карточки ссылками, где переход возможен;
- для неинтерактивных карточек не применять hover как у ссылок.

### 5.4. Отчёт

Блок формирования отчёта визуально отделить от фильтра сотрудников, но не помещать его в крупную дополнительную карточку.

Рекомендуемый вариант:

- компактная кнопка `Экспорт`;
- по нажатию открывается меню/небольшой popover с годом и форматом.

Если popover сильно усложняет реализацию, оставить строку, но оформить её как вторичное действие и выровнять справа.

## 6. Канбан и календарь

Файлы:

- `templates/board.html`;
- `static/style.css`;
- при необходимости минимальные изменения контекста маршрута в `app.py`.

### 6.1. Переключатель представления

Добавить segmented control:

- `Канбан`;
- `Календарь`;
- `Оба`.

По умолчанию — `Канбан`.

Выбранный режим сохранить в `localStorage`, без изменения БД.

Правила:

- `Канбан` показывает только канбан;
- `Календарь` показывает только календарь;
- `Оба` показывает существующий комбинированный режим;
- контент не должен повторно загружаться с сервера;
- переключение производится через CSS-классы/атрибут страницы;
- выбранная кнопка имеет `aria-pressed="true"`.

### 6.2. Терминология

Заменить пользовательскую надпись:

- `Гант` → `Календарь сроков`.

Имена внутренних Python-переменных менять не обязательно, если это увеличит объём diff без пользовательской ценности.

### 6.3. Заголовок канбан-колонки

По умолчанию показывать только:

- drag-handle;
- название;
- счётчик;
- кнопку меню `•••`.

В меню перенести:

- переименовать;
- удалить.

Поле переименования не должно быть постоянно видимо.

Переименование:

- открывается после выбора соответствующего пункта;
- сохраняется существующим POST-маршрутом;
- можно отменить;
- Enter отправляет форму;
- Escape отменяет редактирование.

Удаление:

- использует существующее подтверждение;
- остаётся опасным действием;
- не меняет текущую серверную логику.

### 6.4. Добавление колонки

Вместо постоянно видимой формы показывать кнопку:

- `+ Колонка`.

После нажатия раскрывать компактную форму.

Требования:

- автофокус на поле;
- Escape закрывает форму;
- Enter отправляет форму;
- серверный маршрут остаётся прежним.

### 6.5. Фильтры канбана

Перевести фильтры на общий `.filter-bar`.

Checkbox-фильтры оформить как toggle-chip:

- `Просроченные`;
- `Без исполнителя`.

Добавить кнопку сброса, которая:

- очищает поиск;
- сбрасывает исполнителя;
- отключает toggle-chip;
- повторно вызывает фильтрацию;
- возвращает счётчики колонок.

Показывать общий результат:

- `Найдено: N`.

### 6.6. Карточки задач

Сохранить:

- drag-and-drop;
- срок;
- просрочку;
- исполнителей;
- открытие по клику;
- клавиатурное открытие.

Улучшить:

- hover/focus-состояние;
- ограничение длинного описания до нескольких строк;
- более явный срок;
- не использовать emoji-календарь как единственный маркер;
- выделить отсутствие исполнителя текстом или чипом.

### 6.7. Пустая колонка

Вместо `—` вывести:

- `Пока нет задач`;
- подсказку о добавлении или перетаскивании.

Пустое состояние не должно занимать чрезмерную высоту.

### 6.8. Ограничение по раскладке

Сохранить текущую модель:

```css
.kb-row {
  display: flex;
  flex-wrap: wrap;
}
```

Не добавлять горизонтальный scrollbar канбан-панели.

## 7. Личные задачи

Файлы:

- `templates/todo.html`;
- `static/style.css`.

### 7.1. Упростить карточку

Карточка должна показывать:

- название;
- срок;
- тег;
- основное быстрое действие;
- меню `•••`.

#### Для задач в бэклоге

Быстрым действием оставить редактирование через клик по карточке или отдельную компактную кнопку.

В меню перенести:

- выше;
- ниже;
- делегировать в канбан;
- удалить.

#### Для задач в квадрантах

Быстрым действием оставить:

- `✓ Выполнить`.

В меню перенести:

- редактировать;
- делегировать;
- удалить.

### 7.2. Клик по карточке

Обычный клик открывает существующую модалку редактирования.

Исключения:

- drag;
- клик по кнопке;
- клик по меню;
- клик по форме.

Нельзя допустить двойного выполнения действия из-за всплытия события.

### 7.3. Поиск

Исправить несоответствие подсказки и горячей клавиши.

Рекомендуемый вариант:

- `/` фокусирует поиск;
- `N` или отдельная кнопка фокусирует создание новой задачи.

Если добавляется `N`, не перехватывать её во время ввода и при нажатых модификаторах.

Текст placeholder должен соответствовать реальному поведению.

### 7.4. Счётчики после фильтрации

Обновлять:

- счётчики квадрантов;
- счётчик бэклога;
- общий результат фильтрации.

### 7.5. Пустые квадранты

Показывать:

- `Нет задач`;
- `Перетащите сюда задачу из бэклога`.

Файлы:

- дату последней встречи 1-на-1, если данные уже доступны.

### 8.2. Действия

Оставить основной кнопкой:

- `Редактировать`.

Перенести в меню `•••`:

- экспорт Excel;
- экспорт PDF;
- удаление сотрудника.

Удаление должно находиться в отделённой danger-группе меню и сохранять подтверждение.

### 8.3. Локальная навигация

Добавить вкладки или якорную навигацию:

- `Обзор`;
- `Развитие`;
- `1-на-1`;
- `История`;
- `Проблемы`.

Предпочтительный технический вариант — клиентские вкладки над уже отрендеренными секциями:

- все данные остаются в HTML;
- серверные маршруты не меняются;
- активная вкладка хранится в URL hash;
- прямой переход по hash открывает нужную секцию;
- без JavaScript все секции остаются доступны последовательно;
- вкладки имеют корректные `role="tablist"`, `role="tab"` и `role="tabpanel"`.

Не скрывать контент CSS по умолчанию до выполнения JS, иначе без JavaScript часть страницы станет недоступна.

### 8.4. Секция «Обзор»

В обзор поместить:

- заметки;
- краткую сводку по текущему году;
- активные проблемы;
- последнюю встречу, если она есть.

Не дублировать полноценные формы из других вкладок. Обзор должен быть кратким.

### 8.5. Полугодовые записи

Сохранить существующие поля и серверные формы.

Улучшить:

- смысловое разделение полей;
- короткие пояснения;
- стабильную иерархию заголовков;
- sticky-панель сохранения внутри активной формы на длинном экране;
- явное состояние «есть несохранённые изменения».

Перед уходом со страницы при изменённой форме показать стандартное предупреждение.

После успешной серверной отправки предупреждение не должно появляться.

### 8.6. Год

Выбор года сделать визуально частью раздела «Развитие».

Опасное действие `Удалить год` не должно находиться рядом с обычным переключением года. Перенести его в меню действий текущего года.

## 11. Мобильная версия

Проверить ширины:

- 320 px;
- 390 px;
- 768 px;
- 1366 px;
- 1920 px.

### Требования до 860 px

- верхняя навигация остаётся доступной;
- меню не выходит за viewport;
- вкладки сотрудника допускают горизонтальную прокрутку;
- канбан и календарь не показываются одновременно по умолчанию;
- фильтры корректно переносятся;
- календарь может иметь собственную горизонтальную прокрутку.

### Требования до 560 px

- page actions переходят на новую строку;
- primary-действия занимают удобную ширину;
- меню карточек не выходит за экран;
- подписи не перекрывают счётчики;
- touch-target интерактивных элементов не меньше 44×44 px;
- длинные названия и теги не расширяют viewport.

- Escape закрывает меню и диалоги;
- после закрытия фокус возвращается на триггер;
- интерактивные элементы не реализуются несемантическим `div` без роли и клавиатурной поддержки;
- цвет не является единственным индикатором;
- `aria-expanded` синхронизирован с меню;
- вкладки имеют корректные роли;
- segmented control использует `aria-pressed`;
- поля связаны с `<label for>`;
- icon-only кнопки имеют `aria-label`;
- сообщения об ошибке доступны через `role="alert"`;
- сообщения об успехе — через `role="status"`;
- модальные окна сохраняют существующую фокус-ловушку.

## 13. Техническая реализация

### 13.1. JavaScript

Не создавать новый большой inline-скрипт в каждом шаблоне.

Допустимые варианты:

- вынести общие UI-компоненты в `static/ui.js`;
- оставить специфическую логику страницы в соответствующем шаблоне.

В общий файл желательно вынести:

- action menu;
- collapsible form;
- segmented control;
- tabs;
- show/hide password;
- общие keyboard handlers.

Подключить файл с `defer`.

Перед переносом общих функций проверить порядок загрузки относительно page scripts.

### 13.2. Progressive enhancement

Основные формы должны продолжить работать через обычный POST.

JavaScript используется для:

- открытия меню;
- переключения представлений;
- вкладок;
- раскрытия форм;
- клиентской фильтрации;
- улучшения обратной связи.

JS не должен быть единственным способом отправить критическую форму, если существующая реализация работает без него.

### 13.3. Состояние интерфейса

В `localStorage` допустимо хранить только UI-предпочтения:

- тема;
- режим доски;
- активная вкладка или раскрытые секции.

Бизнес-данные в `localStorage` не сохранять.

### 13.4. Совместимость

Не использовать API без разумной поддержки актуальными Chromium-браузерами, если нет fallback.

Сохранить текущую модель использования `inert` для модальных окон.

## 14. Тестирование

### 14.1. Автоматические тесты

Добавить или обновить тесты на:

- наличие кнопок переключения канбан/календарь;
- сохранение прежних серверных форм и action URL;
- существование всех маршрутов;
- отсутствие удалённых функций;
- наличие доступных атрибутов;
- уникальность HTML `id`;
- наличие label у новых полей;
- корректные danger-классы у разрушительных действий;
- токен Telegram рендерится как password;
- карточка сотрудника содержит все исходные разделы;
- формы записи, встреч, проблем и истории не потеряли поля;
- обычные POST-сценарии продолжают работать.

HTML substring-тесты не считать достаточной проверкой интерактивности.

### 14.2. Browser smoke test

Проверить в реальном браузере.

#### Общие компоненты

- action menu открывается;
- закрывается кликом вне;
- закрывается Escape;
- возвращает фокус;
- пункты доступны Tab;
- меню не прозрачное.

#### Доска

- переключаются три режима;
- выбор восстанавливается после reload;
- перетаскивание карточек работает;
- перетаскивание колонок работает;
- фильтры работают;
- счётчики обновляются;
- переименование работает;
- добавление колонки работает;
- удаление сохраняет подтверждение;
- модалка карточки работает.

#### Todo

- карточка открывает модалку;
- меню не запускает открытие карточки;
- drag-and-drop работает;
- быстрое выполнение работает;
- поиск и горячая клавиша соответствуют подсказке;
- фильтр корректно обновляет счётчики.

#### Сотрудник

- переключение вкладок работает;
- hash открывает нужную вкладку;
- сохранение форм работает;
- предупреждение о несохранённых данных появляется только при реальных изменениях;
- экспорт доступен;
- удаление находится в danger-группе.

#### Настройки

- токен скрыт;
- кнопка показа работает;
- восстановление находится в danger-zone;
- обычные формы отправляются.

### 14.3. Визуальные проверки

В обеих темах проверить:

- контраст;
- границы;
- hover;
- focus;
- active;
- disabled;
- danger;
- empty;
- loading;
- dropdown;
- modal;
- длинные имена;
- длинные названия задач;
- пустые списки;
- большие счётчики `99+`.
